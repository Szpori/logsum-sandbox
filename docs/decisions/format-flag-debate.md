# Architectural debate — logsum output format selection

**Status:** decided  
**Date:** 2026-10-19  
**Kata:** K 5.D.12  

---

## 1. Fork

> Should logsum's output format be selected via `--format` on every invocation, or set once in a project config file (e.g. `.logsum.toml`) and override-able per-run?

---

## 2. Decision criteria

| # | Criterion | Why it matters here |
|---|-----------|---------------------|
| C1 | **Self-documenting invocation** | A command read six months later in a Makefile or CI log must be fully understood without opening a second file |
| C2 | **CI/local parity** | Config files that live outside the repo produce environment-dependent behaviour; logsum is a pipeline tool run in both places |
| C3 | **Zero new parser surface** | `CLAUDE.md` constrains logsum to stdlib only; any config format adds a parsing contract to maintain and document |
| C4 | **Discoverability via `--help`** | All knobs must be visible from one command; a config file requires knowing the file name, location, and schema |
| C5 | **Ergonomics for the common case** | If a team always wants JSON, repeating `--format json` in every call site is noise |

---

## 3. Option A — Flag per invocation

**Claim:** `--format {csv,json}` on every call is the correct long-term interface.

**C1 — Self-documenting** *(evidence-backed)*  
`logsum events.csv out.json --format json` is a complete statement. Every field of behaviour is visible in the command. A CI log or a `git blame` on a Makefile tells the full story without side-channel files. This is the Unix convention for format-selecting flags (`curl -o`, `jq -r`, `sort -t`).

**C2 — CI/local parity** *(evidence-backed)*  
A `.logsum.toml` in a developer's home directory silently changes output format on every invocation. CI has no such file; CI gets a different format; both exit 0. This class of bug — environment-dependent silent behavioural divergence — is documented in twelve-factor app methodology as a first-order reliability concern. The flag eliminates ambient state entirely.

**C3 — Zero parser surface** *(evidence-backed)*  
`tomllib` (Python 3.11 stdlib) is read-only; it parses TOML but cannot write it, so `.logsum.toml` can be read but not self-generated by the CLI. Any config file adds: a file-location convention, a precedence rule (project vs. home-dir vs. system), a schema to document and version, and a new failure mode (malformed config → cryptic error). The flag adds none of these.

**C4 — Discoverability** *(evidence-backed)*  
`logsum --help` is complete. There is no second artefact. A new user, a new CI pipeline, a new team member all reach full understanding from one command.

**C5 — Ergonomics (partial concession)** *(assumption)*  
Repetition is real. The rebuttal — use a Makefile variable or shell alias at the call site — shifts the problem to the caller. That is the correct place for it: different call sites in the same project may want different formats (a human-readable CSV for a dev dashboard, JSON for a downstream pipeline). Baking a default into the tool couples it to a file it doesn't need and makes per-call-site variation harder.

---

## 4. Option B — Config file default

**Claim:** A `.logsum.toml` (or equivalent) with an override-able `--format` per run is better for teams with a stable format preference.

**C5 — Ergonomics** *(evidence-backed)*  
In practice, a team running logsum in a data pipeline commits to one output format for months at a time. Repeating `--format json` in every Makefile target, every cron entry, every CI step is noise — it adds characters that carry no information for that team. A config file externalises a stable preference exactly once.

**C1 — Partial counter** *(assumption)*  
A checked-in `.logsum.toml` at the project root is itself a documented, version-controlled statement of intent. `git log .logsum.toml` tells the history of format decisions. The config file is not invisible; it is a first-class artefact.

**C2 — Partial counter** *(assumption)*  
The CI/local divergence risk is real only if the config file is *not* checked in. A project-root `.logsum.toml` committed to the repo is present identically in every environment that clones it. The risk is operational discipline, not a structural flaw.

**C3 — Parser surface is small** *(assumption)*  
`tomllib` is stdlib. One `tomllib.load()` call, one key read. The precedence rule can be minimal: project-root file only, no home-dir lookup, no system-level file. The schema is one key (`format = "json"`). This is not a meaningful maintenance burden.

**C4 — Discoverability gap is real** *(evidence-backed)*  
This is the weakest point for Option B. `--help` does not mention the config file without extra documentation effort. A new user will not discover `.logsum.toml` without reading docs or finding an example. This is a genuine tax.

---

## 5. Strongest dissent (cross-pollination)

**Against Option A (flag), raised by the config-file side:**  
The Makefile-variable answer to repetition is not ergonomic at scale. A wrapper variable or alias is a second artefact that must be maintained, shared across a team, and re-applied every time someone sets up a new environment. The flag answer moves the problem to the caller and calls it a solution. For a team of ten running logsum 200 times a week, always wanting JSON, this is a real friction cost that compounds over months. The "correct place for defaults is the call site" is an assertion, not a proof.

**Against Option B (config file), raised by the flag side:**  
The "checked-in config eliminates CI divergence" argument requires that every future user knows to check the config file into the repo. It converts a tool-level guarantee (no ambient state) into an operational convention (remember to commit the file). Conventions drift; guarantees don't. The first team member who adds `.logsum.toml` to `.gitignore` or creates a home-dir file "just for local dev" reintroduces the divergence the pattern was supposed to prevent.

---

## 6. Claims assessed

| Claim | Side | Type |
|-------|------|------|
| Flag gives complete invocation story | A | evidence-backed — Unix convention, CI logging practice |
| Home-dir config causes silent CI/local divergence | A | evidence-backed — twelve-factor, environment-parity literature |
| `tomllib` parser surface is negligible | B | assumption — depends on schema scope decision not yet made |
| Checked-in config eliminates CI divergence | B | assumption — requires operational discipline; no enforcement mechanism |
| Makefile variable is an acceptable ergonomic answer | A | assumption — true for small teams; contested at scale |
| Discoverability gap of config file is a real tax | B | evidence-backed — `--help` incompleteness is observable |
| Different call sites in one project may want different formats | A | unknown — no usage data; plausible for logsum's current scope |

---

## 7. Decision

**Keep `--format` as a per-invocation flag. Do not add a config file.**

**Driving criterion: C2 — CI/local parity.**

The config file's strongest argument (C5, ergonomics) is real but solvable at the call site. The flag's strongest argument (C2, parity) is structural: it is a guarantee the tool provides unconditionally, not a convention that callers must remember to uphold. At the point where logsum is used in automated pipelines — the scenario where format consistency matters most — silent environment-dependent divergence is the failure mode that hurts most and is hardest to diagnose. The flag eliminates that failure mode completely.

Secondary driver: C4 (discoverability). `--help` is complete. No second artefact to find.

---

## 8. Reversal evidence

Revisit this decision if any of the following signals appear within 12 months:

1. **Repetition complaints in ≥ 3 separate team reports** — evidence that C5 friction is compounding faster than the call-site mitigation absorbs it
2. **A pipeline that needs two different formats from one project** — would reveal whether the "different call sites want different formats" claim (currently unknown) is real, and whether a config file at project root handles it worse than per-call flags
3. **A `.logsum.toml` appearing in the wild in multiple team repos** — evidence that teams are building the config-file pattern themselves outside the tool, which makes it worth standardising rather than fighting
